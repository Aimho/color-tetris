# 8단계: 미션·커스터마이징 상점·랭크 에너지

## 배포 목표

비공개 테스트 중인 Android 앱에 재방문 동기와 첫 광고 수익 모델을 추가한다. 현재 Play Console 기준 버전은 `0.4.1-alpha`, `versionCode 5`다. 다음 비공개 테스트 빌드는 `0.5.0-alpha`, `versionCode 6`으로 배포한다.

이번 업데이트는 다음 세 기능을 포함한다.

1. 일일·주간 미션과 장식 재화 `SPARK`
2. 보유 아이템과 장착 기능을 포함한 커스터마이징 상점
3. 최대 3개, 30분당 1개 충전, 보상형 광고로 1개를 받는 랭크 에너지

시즌 패스, 피버 타임, 특수 블록, 클랜·길드는 포함하지 않는다. 이번 상점은 `SPARK`만 사용하며 Google Play Billing과 현금 상품은 넣지 않는다. 연습 모드는 에너지를 소비하지 않는다.

## 구현 방식

서버 권한형으로 구현한다. Cloud Functions가 랭크 에너지, 미션 진행도, `SPARK`, 보유 아이템을 확정한다. 클라이언트는 서버 응답을 표시하고 장착 상태만 로컬에 캐시한다. 광고 보상은 AdMob 서버 측 확인(SSV)이 끝난 뒤 지급한다.

로컬 저장만 사용하는 방식은 구현량이 적지만 앱 재설치와 기기 시간 변경으로 보상을 반복 획득할 수 있다. 클라이언트가 먼저 지급하고 나중에 서버와 맞추는 방식은 광고 직후 반응이 빠르지만 중복 보상과 롤백 처리가 복잡하다. 랭킹과 장식 재화가 같은 프로필에 연결되므로 서버 권한형을 사용한다.

```text
게임 종료 ──> 랭킹 리플레이 검증 ──> 미션 진행도 ──> SPARK 지급
                                      │
홈/마이페이지 <── 프로필·에너지·보유 아이템 <── Cloud Firestore
      │                               │
      ├── 랭크 시작 ──> 에너지 소비 ──┘
      │
      └── 광고 요청 ──> AdMob ──> SSV 검증 ──> 에너지 1개 지급

상점 구매 ──> SPARK 차감 + 아이템 소유권 기록 ──> 장착
```

## 1. 랭크 에너지

### 규칙

- 최대 보유량은 3개다.
- 새 계정은 에너지 3개로 시작한다.
- 랭크 실행 토큰을 발급할 때 서버 트랜잭션에서 1개를 소비한다.
- `0.5.0-alpha`는 `startRankedRunV2`를 사용한다. 기존 `startRankedRun`은 정책 우회를 막고 구버전 UI 혼선을 피하기 위해 업데이트 필요 오류를 반환한다.
- 연습 모드와 진행 중인 랭크 복구는 에너지를 소비하지 않는다.
- 서버 오류로 실행 토큰을 만들지 못하면 에너지를 차감하지 않는다.
- 사용자가 실행 토큰을 받은 뒤 게임을 포기하거나 앱을 종료해도 에너지를 돌려주지 않는다.
- 서버 시각을 기준으로 30분마다 1개를 충전하며 최대 3개에서 멈춘다.
- 광고 1회를 확인하면 에너지 1개를 지급한다. 자동 충전과 광고 충전 모두 최대 3개를 넘지 않는다.
- 에너지가 3개인 상태에서는 광고 버튼을 비활성화한다.
- 광고 로드 실패, 중도 종료, SSV 검증 실패에는 에너지를 지급하지 않는다.

### 서버 계산

프로필에 `rankedEnergy`, `energyUpdatedAt`을 저장한다. 서버가 프로필을 읽을 때마다 다음 순서로 현재 값을 계산한다.

1. `elapsed = now - energyUpdatedAt`
2. `refilled = floor(elapsed / 30분)`
3. `rankedEnergy = min(3, rankedEnergy + refilled)`
4. 3개 미만이면 충전에 사용하고 남은 시간을 보존하도록 `energyUpdatedAt`을 30분 단위로 전진시킨다.
5. 3개가 되면 `energyUpdatedAt = now`로 맞춘다.

랭크 시작, 광고 보상, 프로필 조회는 같은 계산 함수를 사용한다. Firestore 트랜잭션으로 중복 탭과 여러 기기 동시 요청을 막는다.

### 화면

- 홈의 랭크 버튼에 `◆ 2/3` 형식으로 현재 에너지를 표시한다.
- 에너지가 0개이면 버튼을 `29:41 후 충전` 상태로 바꾸고 광고 충전 버튼을 노출한다.
- 에너지가 1~2개여도 사용자가 광고 충전을 선택할 수 있다.
- 앱이 포그라운드로 돌아올 때와 분 단위 타이머가 바뀔 때 잔여 시간을 갱신한다.
- 웹과 데스크탑에서는 광고 버튼을 숨긴다. 자동 충전 규칙은 동일하게 적용한다.

## 2. 일일·주간 미션

### 초기 미션

한국 표준시를 기준으로 일일 미션은 매일 00:00, 주간 미션은 월요일 00:00에 갱신한다.

| 구분 | 조건 | 보상 |
| --- | --- | ---: |
| 일일 | 게임 2회 종료 | 20 SPARK |
| 일일 | 블록 80셀 제거 | 25 SPARK |
| 일일 | 리액터 2회 발동 | 25 SPARK |
| 주간 | 게임 10회 종료 | 80 SPARK |
| 주간 | 블록 500셀 제거 | 100 SPARK |
| 주간 | 최대 3연쇄 이상을 3게임에서 달성 | 100 SPARK |
| 주간 | 레벨 10 이상 1회 달성 | 80 SPARK |

연습 결과는 게임 종료 시 클라이언트가 제출하므로 재화 보상 대상에서 제외한다. 랭킹 서버가 재생 검증한 결과만 미션에 반영한다. 게임을 끝내지 않은 실행, 검증 실패 기록, 같은 `runId`의 재제출은 진행도를 올리지 않는다.

완료한 미션의 보상은 별도 수령 버튼 없이 서버가 한 번만 자동 지급한다. 사용자는 미션 화면에서 지급 내역을 확인한다. 시즌이 바뀌어도 진행 중인 주간 미션은 KST 주간 경계를 따르며 월간 시즌과 별도로 유지한다.

### 데이터

- `player_profiles/{uid}`: `sparkBalance`, `missionDay`, `missionWeek`
- `mission_progress/{uid}_{period}`: 미션별 진행도, 완료 시각, 지급 여부
- `ranked_completion_events/{runId}`: 검증된 게임의 미션 반영 이벤트와 처리 상태

Cloud Functions가 랭킹 제출을 승인하는 트랜잭션 안에서 미션 반영 여부를 기록한다. 재시도해도 `SPARK`를 중복 지급하지 않는다.

## 3. 커스터마이징 상점

### 상품 구조

장착 슬롯은 `boardTheme`, `blockSkin`, `clearEffect`, `lobbyBgm`, `profileFrame`, `equippedBadge`로 나눈다. 기존 `REACTOR`, `EMBER`, `AURORA` 테마와 누적 삭제 해금 조건은 유지하고 계정 소유권으로 이전한다.

첫 상점 카탈로그는 기존 Canvas, CSS, 절차적 오디오를 변형해 만든다. 외부 이미지와 음원 라이선스는 사용하지 않는다.

| 상품 | 슬롯 | 가격 |
| --- | --- | ---: |
| NEON GRID | boardTheme | 250 SPARK |
| CRYSTAL | blockSkin | 300 SPARK |
| PULSE | clearEffect | 250 SPARK |
| NIGHT DRIVE | lobbyBgm | 400 SPARK |
| CHROMA LINE | profileFrame | 200 SPARK |

색상 구분, 화살표 방향, 배수 셀 문자는 모든 스킨에서 같은 대비 기준을 유지한다. 스킨은 셀의 판정, 크기, 확률과 점수에 영향을 주지 않는다.

### 구매와 장착

- 서버 함수가 상품 ID, 판매 상태, 가격을 확인한 뒤 `SPARK`를 차감한다.
- 구매와 아이템 소유권 기록은 하나의 Firestore 트랜잭션에서 처리한다.
- 이미 가진 상품을 다시 구매하면 차감 없이 현재 소유권을 반환한다.
- 장착 요청은 사용자가 가진 상품만 허용한다.
- 오프라인에서는 마지막 장착 상태를 표시하지만 구매와 장착 변경은 막는다.
- 상점 카탈로그를 불러오지 못해도 연습과 랭크 플레이는 계속할 수 있다.

## 4. 보상형 광고

Android 앱은 `@capacitor-community/admob`을 사용한다. 이 플러그인은 보상형 광고와 SSV의 `userId`, `customData` 전달을 지원한다. 웹 빌드는 광고 모듈을 동적 로드하지 않는다.

광고 요청 전에 Cloud Function이 10분 유효한 일회용 `rewardRequestId`를 발급한다. 사용자별 미처리 요청은 하나만 유지하며, 유효한 요청이 있으면 같은 ID를 반환한다. 앱은 Firebase UID와 `rewardRequestId`를 SSV 데이터로 전달한다. AdMob SSV 엔드포인트는 Google 공개 키로 서명을 검증하고 다음 조건을 모두 만족할 때 에너지를 지급한다.

- 등록된 보상형 광고 단위에서 온 요청
- 보상 항목이 `energy`, 보상 수량이 `1`인 요청
- 만료되지 않은 `rewardRequestId`
- 요청을 만든 UID와 SSV `user_id`가 일치
- 처음 처리하는 `transaction_id`
- 현재 에너지가 3개 미만

SSV가 늦게 도착할 수 있으므로 광고 종료 화면은 `보상 확인 중`을 표시하고 프로필을 다시 조회한다. 30초 안에 확인되지 않으면 홈으로 돌아가며, 나중에 SSV가 도착하면 다음 프로필 조회에서 증가한 에너지를 표시한다.

개발 빌드는 Google 테스트 광고 단위를 사용한다. 테스트 광고는 실제 SSV를 호출하지 않으므로 Firebase Emulator에서만 서명 검사를 우회한 모의 콜백을 사용한다. 비공개 테스트 빌드에서는 실제 광고 단위와 SSV를 끝까지 검증한다.

앱 시작 시 UMP SDK로 동의 정보를 갱신하고 필요한 동의 화면을 표시한다. 설정에 `개인정보 선택` 메뉴를 추가해 사용자가 동의 상태를 다시 열 수 있게 한다. 앱은 동의 상태가 광고 요청을 허용할 때만 광고를 로드한다.

## 5. 단계별 구현

### A. 공통 설정과 데이터 이전

1. 기본 개발 워크스페이스의 Capacitor 앱 ID를 `com.aimho.games.colorbomb`으로 통일한다.
2. 프로필 스키마에 에너지, `SPARK`, 소유 아이템, 장착 슬롯을 추가한다.
3. 기존 사용자는 첫 서버 조회에서 에너지 3개와 `SPARK` 0으로 이전한다.
4. 기존 테마 해금 기록을 유지하고 해당 아이템 소유권을 자동 부여한다.
5. Firebase Remote Config에 `ranked_energy_enabled`, `missions_enabled`, `shop_enabled`, `rewarded_ads_enabled` 스위치를 추가한다.

### B. 에너지

1. 에너지 계산 함수를 Cloud Functions와 단위 테스트에 추가한다.
2. `startRankedRun` 트랜잭션에 충전 계산과 1개 소비를 넣는다.
3. 프로필 조회 응답에 에너지와 다음 충전 시각을 추가한다.
4. 홈 버튼, 충전 타이머, 에너지 부족 오류 처리를 연결한다.

### C. 미션과 재화

1. 승인된 랭킹 결과를 일일·주간 진행도로 변환한다.
2. 미션 완료와 `SPARK` 지급을 멱등 트랜잭션으로 구현한다.
3. 홈과 마이페이지에 미션 목록, 진행도, 완료 상태를 추가한다.
4. KST 일일·주간 경계와 시즌 경계가 겹치는 경우를 테스트한다.

### D. 상점

1. 상품 카탈로그와 장착 슬롯을 정의한다.
2. 구매·장착 Cloud Functions와 Firestore 규칙을 추가한다.
3. 기존 테마 선택 UI를 보유 아이템 UI로 이전한다.
4. 상점, 미리보기, 구매 확인, 잔액 부족 상태를 구현한다.
5. 다섯 개 초기 상품의 Canvas, CSS, 절차적 오디오 변형을 추가한다.

### E. 광고

1. AdMob 앱과 Android 보상형 광고 단위를 만든다.
2. Capacitor AdMob 플러그인과 UMP 동의 흐름을 Android 프로젝트에 연결한다.
3. 광고 요청 발급 함수와 SSV HTTPS 엔드포인트를 추가한다.
4. SSV 서명, 광고 단위, UID, 요청 ID, 거래 ID를 검증한다.
5. 모의 콜백 통합 테스트와 비공개 테스트 실광고 검증을 진행한다.

### F. 비공개 테스트 배포

1. 전체 테스트와 프로덕션 웹 빌드를 통과시킨다.
2. Android 프로젝트를 동기화하고 `versionCode 6`, `versionName 0.5.0-alpha`로 설정한다.
3. 서명된 AAB를 기존 비공개 테스트 트랙에 업로드한다.
4. 기존 설치 위에 업데이트해 프로필, 테마, 랭킹 기록이 유지되는지 확인한다.
5. 에너지 0개부터 자동 충전, 광고 충전, 미션 지급, 상품 구매를 실제 기기에서 검증한다.

## 테스트 기준

### 정상 흐름

- 신규·기존 계정이 에너지 3개로 시작한다.
- 랭크 시작마다 1개가 줄고 30분마다 1개가 복구된다.
- 검증된 랭킹 결과가 일일·주간 미션에 한 번만 반영된다.
- `SPARK` 구매와 장착 상태가 앱 재설치 후 복원된다.
- 광고 SSV 확인 후 에너지가 1개 증가한다.

### 오류와 중복 요청

- 네트워크 단절, Functions 타임아웃, 광고 로드 실패가 플레이 상태를 손상시키지 않는다.
- 랭크 버튼 연속 탭, 구매 연속 탭, 동일 SSV 재전송이 한 번만 처리된다.
- 만료·위조된 광고 요청과 잘못된 광고 단위는 보상을 지급하지 않는다.
- 미션 기간이 바뀌는 순간 제출된 기록은 서버 수신 시각 기준으로 한 기간에만 반영된다.

### 경계값

- 에너지 `0/3`, `2/3`, `3/3`과 29분 59초, 30분, 60분 경과를 검증한다.
- 광고 확인과 자동 충전이 동시에 발생해도 에너지가 3개를 넘지 않는다.
- 잔액이 가격과 같을 때 구매되고 1 부족할 때 거절된다.
- 기존 `EMBER`, `AURORA` 해금 사용자의 장착 상태가 유지된다.

## 장애, 확장과 롤백

- AdMob 장애 시 광고 버튼만 숨기고 자동 충전, 연습, 보유 아이템은 유지한다.
- Firebase 장애 시 연습 모드만 제공하고 랭크 시작, 미션 수령, 구매를 잠근다.
- 사용자 수가 10배가 되면 랭킹 제출 트랜잭션에 추가된 미션 문서 쓰기가 먼저 비용 압력을 만든다. 사용자·기간별 단일 진행도 문서로 쓰기 수를 제한하고 카탈로그는 Remote Config 캐시를 사용한다.
- 기능 문제가 생기면 새 클라이언트 배포를 중단하고 서버 함수를 이전 안전 버전으로 롤백한다. 구 API는 업데이트 오류를 반환하고 에너지 적용은 V2 API에서만 수행한다.
- 상품을 비활성화해도 구매 기록과 장착 아이템은 삭제하지 않는다. 재화 원장과 광고 거래 ID도 보존해 재활성화 시 중복 지급을 막는다.
- 가장 약한 가정은 보상형 광고가 사용자에게 랭크 대기 시간을 줄일 만큼 가치가 있다는 점이다. 비공개 테스트에서 광고 선택률, 완료율, 광고 후 랭크 시작률을 측정하고 선택률이 낮으면 에너지 최대치와 자동 충전은 유지한 채 광고 버튼만 제거한다.

## 외부 준비 항목

- Google Play Console: 기존 `com.aimho.games.colorbomb` 앱과 비공개 테스트 트랙을 사용한다.
- AdMob: Android 앱 등록, 보상형 광고 단위, SSV 콜백 URL, 개인정보 메시지를 설정한다.
- Firebase: Functions 공개 HTTPS 엔드포인트, Firestore 인덱스·규칙, Remote Config를 배포한다.
- Android 서명: 현재 비공개 테스트 앱과 같은 Play App Signing 연결을 유지한다.
- 개인정보처리방침: 광고 식별자, 맞춤형 광고 선택, Firebase UID, 보상 거래 기록을 반영한다.

AdMob 플러그인 저장소와 Google의 보상형 광고 SSV·UMP 문서는 계획 작성 시점에 접근 가능한 것을 확인했다. 구현을 시작할 때 Capacitor 7과 플러그인의 호환 버전을 잠근다.

## 완료 기준

- 웹과 Android 자동 테스트, Functions 테스트, Firestore 규칙 테스트가 모두 통과한다.
- Android 9 이상 실기기에서 자동 충전과 광고 SSV를 검증한다.
- 기존 `versionCode 5` 설치 위에 `versionCode 6` 업데이트가 성공한다.
- 앱 재설치와 다른 기기 로그인 후 구매 아이템과 `SPARK`가 복원된다.
- 광고 동의를 거부하거나 광고 서비스가 실패해도 연습과 자동 에너지 충전을 사용할 수 있다.
- 비공개 테스트에서 치명적 오류와 재화·에너지 중복 지급이 없는 것을 확인한 뒤 프로덕션 승격 여부를 결정한다.
